# RTX 5060 Ti CUDA occupancy check — 2026-10-04

The fork keeps the upstream Goldilocks and Poseidon2 arithmetic. Its first GPU change adjusts the CUDA kernel's `__launch_bounds__` occupancy target from `(256, 4)` to `(256, 2)` while keeping the same 256 threads per block and the same nonce search. NVIDIA's driver JIT then reports 86 registers and 0 bytes of local memory per thread for `mining_main`, instead of 64 registers and 8 bytes of local memory on the baseline.

Local tests used a 16 GB RTX 5060 Ti, CUDA 13, the same 32 million nonce batch, GPU only, and source builds with Rust 1.93. Alternating 20-second benchmark runs reported 230.20, 233.25, and 230.10 MH/s for baseline, `(256, 3)`, and baseline; median active GPU draws were 132.27, 133.07, and 132.12 W. A later `(256, 2)` / baseline pair reported **234.48 / 230.22 MH/s**, with **131.18 / 131.20 W** median active GPU draws. That is a roughly **1.85%** short-run speed gain at essentially the same sampled GPU power. All runs used the complete miner benchmark; they do not measure whole-computer wall power. Short samples and changing clocks limit the precision of the gain.

The release-mode `engine-cuda` suite passed all 10 tests with the `(256, 2)` kernel, including CPU comparison across nonce carries, field arithmetic, target boundaries, and a CPU-verified solution. A 35-second live Quanpool run logged jobs near 234–235 MH/s. The address-specific pool API increased from 111 to **123 accepted shares**, with zero stale and zero invalid, and reported **0.000010576048 QTC pending** afterward. That pending credit is pool accounting, not an on-chain payout or a sale. The production payout address equals the project fee address, so fee switching was omitted for this local run.

The isolated build and benchmark logs are retained locally under ignored `.runtime/research/quantus-occupancy-tune` and `.runtime/research/quantus-*.log` in the dashboard project. The selected change is two launch-bound numbers; the consensus kernel body is untouched.
